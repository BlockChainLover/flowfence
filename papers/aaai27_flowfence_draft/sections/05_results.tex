
\section{Results}

\paragraph{RQ1: retrieval-memory containment.}
Table~\ref{tab:p0_agentpoison} reports the adapted AgentPoison retrieval-memory comparator. Without defense, the saved P0 axis shows poisoned-retrieval exposure and non-zero attack manifestation. FlowFence-Lite does not claim to prevent every poisoned input from being retrieved internally. Instead, it quarantines or rewrites retrieved content before it is exposed or acted on. This is the paper's containment target: stop contaminated context from becoming unsafe model-visible state or external leakage. Static keyword filtering is strong on this known-trigger same-axis setting, so P0 is used as a retrieval-memory sanity check rather than as a broad robustness result.

\input{tables/table_p0_agentpoison}

The broader P0 evidence also supports a conservative caveat about simple string defenses. A same-axis static keyword filter can block the original known-trigger attack, but a held-out instruction stress test records non-zero attack manifestation for the non-oracle static filter while FlowFence still contains manifestation on the same adapted retrieval anchor. This supports a blocklist-brittleness interpretation; it does not make P0 a broad held-out robustness benchmark. Overhead artifacts are tracked in the claim audit, but they are not a headline result because the strongest paper claims concern containment rather than speed.

\paragraph{RQ2: deterministic propagation.}
The deterministic MAS benchmark establishes that privacy risk depends on the runtime path, not only on the text. After benchmark strengthening, topology effects appear: shared workspace and blackboard pathways create broader contaminated reach than linear handoff. This supports the central framing that multi-agent privacy is a propagation problem. The deterministic evidence is not real-provider evidence; it validates the runtime mechanism and metric suite.

\paragraph{RQ3: MiniMax-backed coverage.}
Table~\ref{tab:minimax_3seed} is the canonical provider-backed result: a MiniMax-backed multi-agent synthetic-runtime coverage experiment. The matrix completed 252/252 runs after retrying one transient timeout. FlowFence-Lite is clean across all 63 configured FlowFence runs, with task success 1.0 and zero raw/external leakage. Against no defense, FlowFence improves raw leakage in 42 groups and ties in 21; it improves external leakage in 32 groups and ties in 31. Against static ACL, it improves raw leakage in 42 groups and external leakage in 30 groups. Against prompt filtering, it improves raw leakage in 18 groups and external leakage in 13 groups, tying the remaining configured groups and never underperforming on these comparisons.

\input{tables/table_minimax_3seed}

Ties should not be read as failures. Many ties occur in no-attack or low-pressure settings where neither method leaks raw content. Improvement counts are most informative in attack-positive settings. Conversely, FlowFence's cascade size need not be zero: the guard can observe a contaminated seed, route it to quarantine, and still prevent unsafe exposure. The privacy-critical outcomes are zero unauthorized raw leakage, zero external leakage, and zero privilege reach in the FlowFence subset.

\paragraph{RQ4: topology and seed stability.}
The MiniMax coverage records a topology effect, and deterministic runs show the same qualitative direction. Blackboard/shared-workspace settings are riskier because one poisoned artifact can be read by multiple agents. Table~\ref{tab:seed_stability} shows that FlowFence is clean on seeds 1, 2, and 3. This does not prove non-MiniMax or production robustness, but it reduces the chance that the main result is a one-seed artifact.

\paragraph{RQ5: comparison with simple baselines.}
No defense exposes expected unprotected risk. Static ACL blocks some hard forbidden movements but cannot govern internal shared-state propagation. Prompt filtering handles obvious direct instructions better than no defense, but it fails on indirect and paraphrased workspace or summary attacks. FlowFence-Lite improves or ties the baselines on configured raw/external leakage comparisons while preserving task success in its own subset.

\paragraph{RQ6: non-oracle held-out validation.}
Table~\ref{tab:nonoracle} addresses the internal-validity concern that an earlier engineering path used oracle attack annotations. The non-oracle variant ignores the attack-applied flag, attack identifiers, attack modes, and oracle labels. Deterministic non-oracle validation completes 540/540 runs with task success 1.0, zero raw/external leakage, and zero oracle-annotation violations. The targeted MiniMax-backed synthetic-runtime validation completes 72/72 runs with the same clean outcome. This substantially mitigates the oracle-annotation and fixed-phrase concerns for the configured held-out paraphrase matrices.

\paragraph{RQ7: mechanism ablation.}
Table~\ref{tab:nonoracle} also reports the no-semantic-pattern ablation. Removing semantic request patterns keeps external leakage and task success tied in the deterministic evidence, but increases raw leakage relative to the full non-oracle variant. This suggests semantic pattern detection contributes to raw-leakage containment, while policy, fanout, safe-view, and quarantine mechanisms still matter. It does not prove that semantic detection is unnecessary, nor does it fully isolate every module.
