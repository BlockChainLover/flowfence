# Outcome-blind D3 selection rule (commit before materialization)

Namespace E2_DEVELOPMENT_V3_D3. Select exactly three new tasks per family from the already-certified 9573 eligible natural records. Do not load questions, golds, model outputs, V1/D2 individual results, failure/reachability/accuracy/privacy data. Inputs are only existing eligible IDs/compatible fact types, cluster metadata and immutable V1/D2-development/confirmatory exclusions; source pins/policy templates are copied as provenance, never ranking inputs.

1. Exclude all eighteen V1/D2 development and all sixty confirmatory IDs. These and the nine new D3 IDs remain permanently development-only / confirmatory as originally assigned; no promotion or replacement.
2. BIRD: group remaining records by database (cluster prefix before `|`). Sort database names lexicographically, take first three nonempty groups and smallest lexical task ID in each. Shared databases with old splits are permitted (the confirmatory set covers all eleven); D3 has three distinct databases.
3. TAT-QA: exclude every context cluster occupied by V1/D2 or confirmatory. Sort remaining nonempty context keys, take the first three and their smallest lexical task ID. No context reuse within or across selected splits.
4. HotpotQA: construct connected components on all existing context-title cluster metadata, joining records sharing any title, exactly as S1-F. Canonical component ID is smallest lexical member ID. Exclude components containing any V1/D2 or confirmatory task. Take first three remaining components in canonical lexical order, then smallest lexical task ID within each. Components/title sets are disjoint across all selected splits. No model-derived rank or category quota. Existing confirmatory bridge/comparison quotas stay untouched; D3 requires diversity of context components, not a new category quota.
5. If any rule has fewer than three candidates, fail for human review; no fallback or relaxation.
6. Fact slots in selection order: BIRD [P4,P4,P4], TAT [P1,P3,P1], Hotpot [P2,P3,P2]. Copy original templates, A/B, authorization and privacy semantics unchanged. Generation ordinals are 79..87 in sorted (family,task_id) order, extending the frozen 1..78 allocation without changing it. Secret IDs retain the existing naming rule. No raw value is materialized in selection outputs.
7. Schedule: sort nine D3 rows by (family,task_id). For cycle c=0,1,2 and row index t=0..8, condition is [CLEAN,A,B][(c+t)%3]; adjacent arms are [EXACT_IFC,FLOWFENCE_R2] when (c+t) is even, reverse otherwise. Each condition has eighteen cells and nine cells per arm. Assign unique cell_id E2_DEVELOPMENT_V3_D3_001..054; repetition=1. This rule is frozen with selection, before IDs and before any live call.

The selection script and this document must be committed before invocation on actual pool metadata. Materialized outputs record the full D3_SELECTION_RULE_COMMIT and are committed later. Existing confirmatory quotas P1=15/P2=15/P3=10/P4=20 and sixty task IDs/policies remain byte-identical. Selection does not authorize D3 execution.
